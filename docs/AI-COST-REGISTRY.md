# AI cost registry

Every AI feature in MythScribe, what starts it, and what one call costs. Generated by
`npm run eval:ai -- -u` from the code (`src/main/ai/eval/costRegistry.ts`) and the hand-written
notes in `src/shared/aiCostNotes.ts`; a new AI feature does not compile until it has a note. The
git history of this file is the log of each feature's cost over time (author request 2026-10-08).

- Tokens are the eval fixtures' estimates (characters / 4): "typical" is the median fixture,
  "worst" the largest fixture (or the input budget when a feature has no prompt). Output is the
  note's typical estimate and the feature's `max_tokens` cap for the worst case.
- Own key (OpenRouter) uses the default models: fast `deepseek/deepseek-v4-flash`, strong `deepseek/deepseek-v4-pro`. OpenAI uses fast `gpt-5.4-mini`, strong `gpt-5.4`. Hosted is the OpenRouter cost plus the 25% markup.
- Estimates only: the ledger (Settings › AI › Usage history) and the developer tools record
  real tokens and cost per request. Use them to correct the typical sizes here.

## When each runs, and ideas to make it cheaper

### `ghostText` — Ghost text

- **When:** VibeWrite on: after a pause, at most once per 12 new characters (the first at a spot is free); capped per day.
- **Ideas:** The most frequent call: keep the caret window small; stable prefix for provider caching; consider a smaller/faster model; skip when the author is deleting. Story memory v2 (F-16.14) sends ghostText.v5: the Story notes block in the bible’s slot within the same 150-token ghost budget and no separate scene steer (the labels are in the block), so a v2 request is a little smaller than v4 (fixtures: 960 vs 1,024 tokens typical, 1,963 vs 2,085 worst).

### `tags` — Tag suggestions

- **When:** Recommend in the Tags column for one scene.
- **Ideas:** Could reuse the summary pass (which already returns tags) instead of a separate call.

### `summary` — Scene summaries, story bible, and tags

- **When:** Indexing: once per scene after edits settle (content-hash cached), and for every stale scene after open; a new prompt version re-reads the book only after the author confirms the cost (F-9.14 conversion dialog); summary.v5 (mood and theme, F-5.6) re-reads nothing: a summary.v4 scene gets them with its next reading.
- **Ideas:** The biggest background spend on a large book: batch API when latency allows; skip tiny edits; cap scene text sent; one pass also yields facts, tags, the scene card, relationships, and thread events (summary.v4 added about 150 output tokens, summary.v5 about 20 more for the mood and theme); drop empty lists from the JSON shape if the ledger shows cut-offs.

### `chat` — Assistant chat

- **When:** Plan-mode brainstorming and Author-mode drafting from the chat. Story memory v2 (F-16.14) sends chat.v6: the Story notes block (400-token budget) in the bible’s slot, no separate steer; a little smaller than chat.v5 (fixtures: 708 vs 749 tokens for Plan, 1,264 vs 1,350 for Author), and the worst case fills the same 8,000-token budget.
- **Ideas:** Trim history turns sooner; keep the voice block only where prose is written.

### `authorMode` — Author mode

- **When:** Author-mode placement (shares the chat prompt: chat.v5, or chat.v6 with the Story notes block in story memory v2; no prompt of its own).
- **Ideas:** Folded into chat/agent drafting; candidate for removal from the feature list.

### `query` — Story Intelligence

- **When:** A question about the book (Query answers with citations).
- **Ideas:** Strong tier with a large retrieval context: fewer full scenes, more summaries; cache by question+context hash.

### `critique` — Editor's notes

- **When:** Editor's notes on one scene. Story memory v2 (F-16.14) sends critique.v4: the Story notes block (400-token budget) in the bible's slot; about 40 tokens less than v3 (fixtures: 1,223 vs 1,264 typical, 7,001 vs 7,025 worst).
- **Ideas:** Long scenes are head-truncated; split very long scenes instead of truncating.

### `embeddings` — Search indexing

- **When:** Not built: reserved for semantic search indexing.
- **Ideas:** If built, use a cheap embedding model and content-hash caching.

### `rewrite` — Rewrite in my voice

- **When:** Rewrite a selection (bubble, chat, or agent edit).
- **Ideas:** Strong tier since 2026-10-10 (author: voice matters more than cost here); on an OpenAI key that is about 3x the fast tier, on the OpenRouter defaults about the same. Answer length tracks the selection: set max_tokens from the selection size. rewrite.v4 adds the scene mood and theme (about 25 input tokens, from the stored reading, no extra call). Story memory v2 (F-16.14) sends rewrite.v5: the Story notes block (400-token budget) in the bible’s slot and no separate steer; about 100 tokens less than v4 (fixtures: 841 vs 936 typical, 2,659 vs 2,802 worst).

### `brief` — Scene brief drafts

- **When:** Draft a scene brief from the scene text.
- **Ideas:** Could reuse the stored summary instead of the whole scene.

### `betaReader` — Beta reader

- **When:** Beta reader reaction to a scene, reading earlier summaries (betaReader.v1). Story memory v2 (F-16.20) sends betaReader.v2: the earlier scenes as their card gists (a map the reader may relate to, never quote), quotes checked in code against the current scene; fixtures 710 vs 673 tokens typical (a longer rule), 10,981 vs 11,599 worst (gists are shorter than summaries with key points).
- **Ideas:** Strong tier: try fast tier with a tighter rubric and compare quality.

### `importStructure` — Import structure detection

- **When:** Detect chapters/scenes in an imported manuscript, one request per ~2,500 words (importStructure.v1, story memory v1). Story memory v2 (F-16.15): importStructure.v2, the same without the tag bank and tag output.
- **Ideas:** Local heuristics first, AI only for ambiguous breaks; batch API (not latency sensitive).

### `continuity` — Consistency check

- **When:** After a scene summary (background) and on demand (Check consistency).
- **Ideas:** Only send paragraphs with candidate conflicts (already done in the background path); skip unchanged scenes.

### `proofread` — Proofread

- **When:** Proofread a scene or a selection.
- **Ideas:** Local spellcheck first; send only paragraphs that changed since the last proofread.

### `whatNext` — What comes next

- **When:** What should come next? Three directions for the scene. Story memory v2 (F-16.14) sends whatNext.v4: the Story notes block in the bible’s slot, no separate steer; about 100 tokens less than v3 (fixtures: 968 vs 1,079 typical, 2,885 vs 3,027 worst).
- **Ideas:** Cheap already; cache per caret context.

### `route` — Assistant routing

- **When:** Classifies an Auto/Ask message to pick the feature (skipped for exact action names). Since route.v2 (F-5.26) it also picks an edit pass (its type or "ask", and the selection, scene, or chapter): ~200 more input tokens in the cached system turn, ~15 more output tokens on an edit request.
- **Ideas:** Local keyword match first; merge into the agent step to save a round trip. A quick pick on an edit request (F-5.26) costs no routing: it starts the pass directly.

### `synopsis` — Synopsis suggestions

- **When:** Suggest a synopsis for a scene (synopsis.v1, with the stored summary). Story memory v2 (F-16.20) sends synopsis.v2: the scene card in the summary’s place; fixtures 580 vs 495 tokens typical, 3,531 vs 3,400 worst.
- **Ideas:** Derive from the stored summary without re-sending the scene.

### `notesSuggest` — Notes suggestions

- **When:** Suggest key points for a scene’s notes. Story memory v2 (F-16.14) sent notesSuggest.v3: the Story notes block in the bible’s slot. Since F-16.20 it sends notesSuggest.v4: the scene card in the summary’s place, and the block carries the scene’s lasting values and mood; fixtures 1,006 vs v3’s 961 tokens typical, 4,892 vs 4,802 worst.
- **Ideas:** Share context building with synopsis; one call could answer both.

### `voiceNotes` — Learned style notes

- **When:** Learned style notes: about once per 5,000 new words of the author’s own prose.
- **Ideas:** Rare and cheap; could run on the batch API.

### `editPass` — Edit passes

- **When:** An Editor-tab pass: one request per scene piece across the chosen scenes. Since F-5.26 also from the chat ("make this scene better", a quick pick, or a specific request), on the selection (one request), the open scene, or a chapter; the chat shows each choice’s estimate first.
- **Ideas:** The largest single job: batch API, fast tier for copy/proofread passes (already), skip unchanged scenes on re-runs. editPass.v2 adds the scene mood and theme to developmental, line, and custom pieces only (about 25 input tokens each, from the stored reading). Story memory v2 (F-16.14) sends editPass.v3: a continuity piece is checked against the Story notes block (up to 400 tokens, its continuity form with no label lines) instead of the sheet references (worst continuity piece 3,641 vs 4,692 tokens), and a scene with no Pinned line to check against sends nothing; every other pass type is v2’s messages, so its cost is unchanged.

### `agent` — Assistant lookups and edits

- **When:** Auto/Ask/Plan chat: research steps then an answer (up to 6 lookups; since agent.v6 a ladder: lookup ≤ 1,200 characters, scene cards ~100 tokens each, local passage search, whole scenes last); prose drafts stream separately. Since agent.v7 (F-5.25) a bulk delete is one clear edit answered without lookups (the clear itself runs locally, no AI); the bulk rules, the organise rule, and the bulk and story-bible edits add ~250 input tokens to a read request and ~470 to a write request (a cached prefix). Since agent.v8 (F-5.25 fixes 5, 7, 8) the write edit list gains status, To do settle, notes clearing, undo, summaries, and open: ~110 more input tokens on a write request, none on a read request; the todo tool prints a short ref per item (~2 tokens each). The actions themselves run locally (summaries queue the existing summary jobs).
- **Ideas:** Check the agent.v6 ladder against the ledger (fixtures: a fact question: the answer step 44 % less input than v5, the whole three-request run 25 % less); fast tier for lookup steps, strong only for the answer; answer a lookup-only question in one step.

### `contextImport` — Context library sorting

- **When:** Sorting uploaded worldbuilding files: one request per ~8,000-character piece (contextImport.v2, story memory v1). Story memory v2 (F-16.9) files a Research page into Pinned instead (contextImport.v3): once per page, after the estimate, one request per ~8,000 characters of its canon text, strong tier with reasoning off; about 3,200 tokens in and 1,500 out per chunk, so a 20,000-word page is ~14 requests, about 15¢ on an own key.
- **Ideas:** Fast tier for simple lists; skip unchanged files (already); batch API. Filing (v3): a smaller chunk for dense pages if the ledger shows cut-offs; skip paragraphs that only restate what Pinned says (a local pre-check).

### `reviewChat` — Upload review chat

- **When:** A message on the upload review screen that changes the pending plan (reviewChat.v2, story memory v1). Story memory v2 (F-16.9): a message on the filing review (reviewChat.v3), strong tier with reasoning off; a little smaller than v2 (fixtures: 580 vs 670 tokens typical, 3,909 vs 5,618 worst).
- **Ideas:** Send a compact review summary instead of every record.

### `planLinks` — Plan links

- **When:** About 20 s after a summary run (and from Find links): links planned scenes and template beats to the written scene that fulfils them (planLinks.v1). Story memory v2 (F-16.21): code matches each plan against the card lines after a reading at no cost; planLinks.v2 picks between an ambiguous best two at most once per reading, only when the reading moved one of their card lines, reasoning off and cached (fixtures 211 tokens typical, 872 worst, vs v1’s 243 and 5,928).
- **Ideas:** Skip when no planned beat is open; match locally by title/summary words first and ask the AI only for ambiguous ones.

### `organise` — Organise

- **When:** Organise (button, the quiet offer, or the chat): one request per chunk of the tags, sheets, notes, and outline listing (up to 16 chunks, reasoning off); a chunk whose answer is cut off is halved and each half sent again, at most twice.
- **Ideas:** Send only the local findings for a quick tidy; skip sections the instruction does not name (already); fast tier for tag-only runs.

### `todo` — To do list: gaps and suggestions

- **When:** Only when you click Check the whole book (one request per window of scene cards, at most 3); and one small request per To do card when its suggestions are first shown.
- **Ideas:** Fold suggestions into the check for the top items; skip the check when no card changed meaningfully (an identical input already sends nothing).

### `sheetSync` — Sheet write-ups: Structured and Blank page kept in step

- **When:** Thirty seconds after the author stops editing a sheet whose fields or page changed (or on Write up now / File now): one write-up when the fields moved, one filing per 3,000 characters of added page text when the page moved; nothing while the hashes say both views agree; identical requests answer from the local cache.
- **Ideas:** Write up only the sections whose fields changed (keep the rest of the page); skip a filing when the page edit is whitespace or punctuation only; batch several sheets edited in one sitting into one request.

### `reader` — Story memory reading

- **When:** Story memory v2 (F-16.17): reader.v1, fast tier, reasoning off. Only when a finished sentence of a scene changed (a local gate decides, nothing is sent while typing): the changed paragraphs ±2 when the author leaves the scene or pauses (from P2a slice 3; Read now meanwhile), the whole scene in pages of 2,500 prose tokens on a first read, after half of it changed, or after five window reads. One request per window piece or page; a reply cut off at its cap is read again once from the last paragraph it quoted. The rules and the roster are a stable prefix (provider caching), the roster rebuilt only on a removal, rename, merge or split. Design figures: about 4,000 tokens in and 300 out for a window, 3,800 / 520 for a first-read page.
- **Ideas:** Skip the card when it is not due (already: +120 output only then); a smaller window when the edit is one sentence; batch Rebuild memory through the provider batch API; measure the cut-off rate in the ledger and trim the claim list before raising the cap.

### `verify` — Story memory check

- **When:** Story memory v2 (F-16.17): verify.v1, fast tier, reasoning off. Batches per reading page (at most 13 facts each, so every verdict fits), only for the facts code could not prove (each with its sentences ±1, and for a she or he up to eight sentences back to those naming whoever it could mean), the card POV, year and flashback, and who is on the page; nothing when code proved everything. max_tokens min(400, 20 + 28 per fact + 12 per card or on-page check); a batch cut off at its cap asks its unanswered items once more. From P2a slice 3 also the spot checks after Rebuild memory: 50 literal facts on the fast tier in batches of 10, 20 verified facts on the strong tier one per call (40 tokens out). On request (F-16.18): Not right › Not about is one fast call per use, one fact with the picked record and every record named in the eight sentences before it, its sentences ±3 (about 400 tokens in, about 40 out); nothing is sent for Wrong value or a line whose sentence changed. Design figures: about 1,300 tokens in and 110 out per batch.
- **Ideas:** Prove more in code (literal patterns per slot) so fewer items are sent; fold presence checks into the reader once the live run shows they agree; the strong spot check only while the proof agreement is new.
